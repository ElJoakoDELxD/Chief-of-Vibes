## 6. Repositories and branches

The public template repository is the canon: untouchable public property. Nobody works on it, and it changes only through a reviewed pull request.

**Your first act, and the system's first proof of utility, is making your own copy:** a repository you own. A session standing on the canon, or on a fresh clone of it, creates that repository for you when it holds a tool that can. The onboard skill carries the procedure (§9). *Use this template*, or a fork, is the button when it does not. Agents are generated, and all work happens, in your copy and never in the canon.

**Which is also where a change is born.** The canon holds the master version; a copy holds the superset, because a copy is the only place a rule can be run against real work before anyone else inherits it. Writing a fix in the canon first makes it universal by default, and a rule that starts universal has never been argued with. So the flow has a direction on the way up as well as down: measured here, proven here, then proposed there. A copy that is *ahead* of the canon is the system working, and the missing step is a pull request rather than a sync.

**What belongs on `main`, and the question that decides it.** `main` is not the repository's tidy half. It is the product: the only thing that ever gets copied, so its contents are the whole of what anybody receives. One question settles any file, and anybody can ask it without re-deriving the rule.

> **Does a fresh copy need this to become itself?**

Yes puts it on `main`. No puts it on the agent branch. Both halves have a failure and most people guard one. **More than needed** ships a claim about somebody else: a file describing one agent, one Principal or one project reaches everybody and describes nobody who receives it. **Less than needed** makes copies diverge on their first day, because each has to be told or invent its own. So the rule is not *keep `main` small*. It is **keep `main` exact**. `tools/pr-guard.sh` enforces it by path and cannot enforce it by content, which is why a proposal is read by a person as well.

The line that keeps getting crossed is definition against instance. **A filled form is identity; an empty form is direction** (§5). The frontmatter schema travels and a filled `state.md` does not, the handoff shape travels and a handoff note does not, and what a post is travels while which post an agent holds does not. When a form on `main` turns out to have been filled, the form stays and the filling moves to the agent — that is a defect to repair rather than a file to delete.

**Which repository am I in?** This is not a judgment call, and neither marker ships. Custody belongs to the post that holds it (§9), so the canon's role branch carries `.canon`, naming the canon as `owner/repo`, and a copy's carries `.blueprint`, naming the blueprint it came from. **`.blueprint` present means derived**, whatever else is on disk: absence of provenance is what makes a repository the root, so nothing has to assert it. Onboarding writes `.blueprint` from the repository the session was standing in before its remote was repointed, and asks rather than guessing when it cannot tell. Neither file, and neither remote, means the question is unanswered, so the session says so and asks. A wrong guess puts an agent's memory in the wrong repository.

**A check that cannot be answered where it runs does not run there.** `tools/pr-guard.sh` asks two questions and only one needs identity. Whether a change is only template files needs none, so it stays on the pull request, mechanical and covering a stranger's fork. Whether this repository issues the master version needs the marker, and a checkout of a pull request's head carries none — so the post asks it, by running the same tool from the branch that holds the post, against the two refs. Answering it there instead of guessing in CI is what stops a rail from reporting a check it never ran (§1, §3).

**A copy of a copy still proposes to the blueprint.** It does not proxy through the copy it came from; it only knows that it was copied from a copy, and that fact lives in `.blueprint` for the drift check and in a line of the copy's own README for a person. If an intermediate is ahead of the blueprint it is holding changes it has not proposed, which is its debt and not something its copies inherit. Sideways propagation would split the canon into dialects.

**Everything is proven outside its own `main`, then proposed upward.** The shape is the same at every level and the canon is only the level with nothing above it: work happens on a disposable branch, the post prepares the door, a person merges. A change landing in a copy's `main` is not finished. It gets a verdict out loud — it travels, or it stays and says why — and neither answer may be the default, because a default is what lets a finding die where it was found (§9). The gate upward binds on three at once: **agnostic**, describing nobody in particular; **an improvement**, so somebody else is better off holding it; and **verified**, run here against real work. Naming which one a change failed is the whole content of the verdict.

**`README.md` is the one template file that becomes identity the moment a copy exists.** The canon ships one so a fresh copy is not empty, and it is addressed to a reader standing on the canon, which is wrong the moment somebody reads it inside a copy. So the agent rebuilds it for that repository: whose it is, what it is for, which agent lives there, and where it came from. The second hop already keeps the branch's own; **the first hop must keep the copy's too**, and that hop is a pull request an agent opens rather than a script anybody can fix, so the rule lives here where the agent opening it reads.

Inside your copy there are two tiers:

- **`main`, the template mirror plus what the repository knows.** It is read-only in operation. It carries no agent and no agent memory. It holds two things: the template synced from the canon, and `knowledge/` (§5). Both change only by a pull request you approve. The guard hook blocks all work on it. For the hard guarantee, enable GitHub branch protection on `main` and require a pull request before merging. Hooks and CI are rails; the server-side rule is the lock.
- **The agent branch, the home.** It is created at onboarding and carries `memory/` and `projects/`. Everything durable lands here.

A chat surface may open on its own branch, as Claude Code web's `claude/*` does. That is scaffolding for template work, and not a place for an agent to live. **An agent session's first act is to check out its own branch**, the one named in `state.md`. Every commit lands there directly. Memory left on a disposable branch is memory waiting to be lost. Only if the surface refuses the checkout does the agent work where it stands. It then pushes before the session ends, and says plainly that it did so. Template maintenance is the opposite case and keeps the disposable branch, deleted once its pull request lands. The branch list is live work, not a graveyard. `git branch --show-current` is ground truth, and a document naming a different branch is stale.

Template updates flow one way: canon, then your `main`, then the agent branch, via `tools/sync.sh`. The first hop is *Sync fork* for a fork, and a pull request otherwise. **Use this template** leaves an unrelated history with no *Sync fork* button. There the agent opens a pull request bringing the canon's template across wholesale. That hop is the agent's job, since it is a pull request the agent can open, so it is never a backlog item (§3). Approving the merge is the Principal's.

The second hop is a **merge**, which is why drift there cannot happen (§1) rather than merely being detected. Git carries each resolution forward through the merge base, so a conflict settled once stays settled, and the branch *is* `main` plus `memory/` and `projects/`.

Conflicts resolve without asking. Template files take `main`'s version, and the agent branch's own `README.md` keeps the agent's (§4). Both outcomes print, and an overwritten template file is named, because the branch had edited something it does not own. Anything the rule does not cover stops the script. Every sync is `--no-ff`, so each one leaves a single merge commit and `git log --first-parent` reads as the agent's history alone. Nothing is hidden; only the default view changes. After a sync the agent tells the Principal what changed, in plain language.

**One language for the template, any language for the agent.** The canon and every copy's `main` are written in English, and that covers everything on disk rather than prose alone: file and folder names, fixtures, commit messages, branch names and pull request bodies. A path is inherited by every copy, so a canon with two naming conventions teaches both. The agent's reply is the one surface that moves: it defaults to the agent's configured language and the Principal may ask for another on any single reply, which changes nothing about what gets written down. The agent replies in its own configured language (§9), and `memory/` is in whatever language the work happens in. The two never meet, because the agent is the interface. The specification stays uniform while each Principal works natively. A Principal who reads no English still governs a system whose rules are English. So a proposal travels upstream **in the template's language**, translated by the agent, whatever language the failure was found in. A canon accumulating in several languages stops being readable by the agents that inherit it. The pool is worth having only because any copy can read what any other copy learned.

### Merge for the template, cherry-pick for the world

Cherry-pick keeps the opposite job. `main` is **vertical**: the branch wants all of it, always, so that flow is a merge with no decision in it, which is rung 1. Everything else is **lateral**, such as another repository, a utility, or a technique read somewhere. There the agent wants one thing and never the whole history. Fetch the source and pick the commit, or lift the idea and write it in this system's own words. Absorption is rung 4 and cannot climb, because every instance judges fit, cost, and what it drags in. Its obligations are already stated: lineage attribution in the README for anything whose articulation shaped this one, and §7's IP hygiene for anything published.

**A template change is not finished when it merges into the canon. It is finished when it governs the repository the agent works in.** A copy on an older spec obeys superseded rules with the old rails wired in, and nothing looks wrong. The guard that fires is the old one. The limit written upstream last week is simply absent. So the version of `SYSTEM.md` on the canon and on your `main` are kept equal. The drift check reports the gap at session start (§1). Closing it comes before substantive work rather than after.
